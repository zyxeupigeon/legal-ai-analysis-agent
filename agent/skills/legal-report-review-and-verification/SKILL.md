# 法律科技分析报告审阅与联网复核 Skill

## 1. 适用场景

当用户上传分析报告类附件，并要求审阅、优化、联网核验、竞品比较、结论调整、量化建模或正式交付时使用。

典型场景：
- 法律科技企业标杆分析；
- 企业与产品竞品研究；
- 行业分析报告；
- 商业模式与经营质量分析；
- 风险、合规与数据安全审查；
- 市场规模、收入空间和估值模型；
- 报告改写、结构优化、图表重制和版本交付。

## 2. 总目标

在不改变报告核心事实和原有意图的前提下，提升准确性、逻辑性、专业性、完整性、可读性、证据可追溯性、结论审慎性和正式交付质量。

不得编造、篡改、补全或默认未经证实的信息。

## 3. 核心工作原则

### 3.0 产品身份与权限闸门
新建法律 AI 产品报告时，产品名称是启动正式分析的唯一必填输入。名称可能对应多个对象、只有泛称或功能描述、疑似错误且无法唯一纠正时，只做最低限度公开身份辨析，并用一个简短问题请用户确认；尽量给出二至三个候选产品和运营主体。确认前不扩展产品生态、不形成正式研究结论、不起草报告、不生成 Word，也不写入产品知识记录。不得根据搜索排序、名称相似度或常识自行选择。

任务涉及登录、付费内容、账号、受限数据库或电脑/浏览器操作时，执行受限动作前必须取得明确同意。无需授权的公开研究可以继续，但未查看的受限功能不得写成已核实事实；受限部分会影响对象边界或核心结论时，只能受限完成，不得交付冒充完整结果的报告。

### 3.1 以参考附件的结构为主
先完整读取附件并区分两类材料：用于模仿的参考报告、用于证明事实的证据材料。

- 参考报告决定报告骨架、章节顺序、分析维度、标题层级、篇幅密度、表格组织和洞察总结风格；
- 多份参考报告并存时，先提取结构清单，选择最适合本次对象的一份作为主骨架，再吸收其他附件中更好的局部写法；
- 初稿或优化稿与参考附件不一致时，逐项比较两种安排对本次对象的适配性、信息密度和论证效果，保留更优者；偏离幅度较大时，先向用户说明并取得同意；
- 允许为适配目标企业进行小幅增减、调序和标题调整，但不得在未确认时改造成另一类报告；
- 每轮优化后重新对照参考附件检查章节、分析角度和洞察总结，防止连续修改导致结构漂移；
- 参考报告只用于模仿结构和写法，不得引用为事实来源、论据或企业信息。除非某附件本身就是本次研究对象的原始证据材料，且用户明确允许使用；
- 附件不支持、公开来源也无法证明的判断，不得以常识或推测补齐。

### 3.2 低风险修改可直接执行
可直接实施：
- 错别字、标点和语病修正；
- 语句润色；
- 重复内容精简；
- 格式统一；
- 标题层级优化；
- 表格排版优化；
- 逻辑衔接补充；
- 不改变结论实质的限定语；
- 明显数字笔误、标签、单位和日期修正；
- 区分“事实”与“企业声明”。

### 3.3 重大优化必须先确认
以下修改不得直接写入最终稿，必须先说明并等待用户确认：
1. 重构整体结构、合并或删除主要章节；
2. 大幅增删核心内容；
3. 新增重要分析维度；
4. 改变分析框架或论证路径；
5. 修改、强化、弱化或推翻核心结论；
6. 删除重要数据、案例或原始判断；
7. 新增实名竞品及统一评分模型；
8. 新增市场规模、收入、估值或财务预测；
9. 相对参考附件显著改变主体章节、分析维度、篇幅分配或报告类型；
10. 任何显著改变读者对用途、风险、结论或责任理解的修改。

重大优化建议必须说明：拟修改内容、修改理由、预期收益、可能风险、不修改的影响。

需要提出重大优化时，按 [重大优化确认模板](references/major_change_confirmation_template.md) 逐项说明并等待用户确认。

## 4. 附件读取异常处理

如出现文件损坏、页面缺失、内容截断、表格或图表无法识别、文字模糊、格式解析异常、数据无法读取或关键内容歧义，立即停止正式优化。

必须说明：
1. 具体问题；
2. 受影响页面、章节或数据；
3. 对优化准确性的影响；
4. 需要重新上传、转换格式或补充的材料。

在确认附件可完整读取前，不得交付正式优化稿。

## 5. 联网复核规则

### 5.1 必须复核的内容
企业主体、核心产品名称、同企业其他 AI 产品与开放平台、官网功能、价格与套餐、融资、客户或用户数据、时间线、行业协会身份、政策法规、安全与隐私承诺、公开案例、图表数据、竞品功能和结论依据。

### 5.2 来源优先级
1. 政府部门、监管机构、国家法律法规数据库；
2. 企业官网、价格页、条款、隐私政策、官方文档；
3. 行业协会、官方会议、官方园区或投资机构；
4. 原始研究、正式公告、权威数据库；
5. 权威媒体；
6. 转载和搜索摘要仅作线索，不作唯一依据。

### 5.3 复核结果处理
- 小问题：直接修正；
- 重大问题：说明后等待确认；
- 无法确认：在内部降低结论强度；正文确需使用时，说明来源并采用“据企业官网/媒体访谈/研究机构文章”等准确归因，不把弱来源写成确定事实；
- 公开承诺不能写成独立验证事实；
- 媒体口径不能替代企业后台或合同数据；
- 缺少统计口径的数据不能用于收入推算。
- 不因来源层级较低而机械添加“建议进一步核验”“正式尽调中应交叉核验”等免责声明。只有未解决的不确定性会实质影响报告结论、决策或风险判断时，才在相应位置简要提示。
- 证据边界只写该来源能够证明和未披露的关键事项，不追加“本报告不将其视为……”等关于写作处理过程的说明。

### 5.4 公开来源、访问障碍与冲突数据
- 数据优先使用当前可公开访问的最高等级来源；最高等级来源缺失时，可以降级使用次一级来源，但必须降低结论强度并标注来源性质；
- 同一数据存在多个公开口径时，不得自行挑选最有利或最完整的数字。优先核对统计日期、定义、币种、是否含税、是否为合同额/授权上限/确认收入、是否为企业声明或第三方估算；
- 无法消除冲突时，并列主要口径，说明差异及其对结论的影响，不将任何一个口径写成确定事实；
- 公开资料可以检索到但因登录、验证码、地区限制、付费墙、robots限制或权限不足无法读取时，提供原始链接、页面名称、建议查询字段和该页面预期能够证明的事项，由用户人工核验；
- 搜索摘要、聚合页和转载页只作线索。若原始页面无法访问，应标注“原始来源未直接读取”，不得把转载内容升级为已核实事实；
- 对关键来源记录访问日期；对可能动态变化的价格、用户数、融资、认证和产品功能设置资料截止日。
- “访问日期”用于说明动态网页在何时被读取，并不表示该事实发生于该日。对网页、价格页、产品页和会更新的数据库记录访问日期；对发布日期明确且内容固定的正式文件，可优先写发布日期，不必机械重复访问日期。全文采用统一格式。
- 来源层级、访问障碍和结论强度主要用于内部判断。除非用户要求审计式证据展示，或该限制会实质改变结论，不在正文中反复设置“证据性质”“本报告处理”“免责声明”等栏目。
- 产品身份明确但公开资料不足时，按证据实际缩减或删除模板模块；不得为了维持章节数量、篇幅、表格或图表完整而使用常识、旧报告或弱相关材料补齐。证据不足以形成完整报告时，交付受限范围并明确不能证明的关键事项。

### 5.5 主张—证据登记与矛盾日志
对企业分析和标杆报告中的关键主张建立 `claim_evidence.json`，至少记录：`claim_id`、`claim_text`、`claim_type`、`category`、`source_url`、`source_tier`、`accessed_at`、`report_location`、`included_in_report`。分析判断还要用 `based_on_claim_ids` 指向其证据主张。当前模型版本、当前产品版本、价格、运营主体和政策状态属于高风险动态事实，只有本轮实际读取的一级官方来源才能支持其进入正文；模型记忆、搜索摘要或未列入来源表的链接均不够。未核验主张必须设置 `included_in_report=false`。

遇到下列情况建立矛盾日志：同一指标数值冲突、企业名称或主体混用、时间线不一致、客户数量与用户数量混用、签约与上线混用、合同金额与确认收入混用。矛盾未解决前不得据此进行财务推算或强结论。

主张—证据登记表和矛盾日志默认作为内部工作底稿，不自动写入最终报告。只有用户要求证据审计、争议复核，或未解决矛盾会实质影响结论时，才把必要部分交付给用户。

### 5.6 企业、品牌、产品与未声明实际状态核验
涉及企业主体、品牌、产品、网站、客户端和开放平台时，先分层核验，不因名称近似、界面相似或域名跳转而直接认定为同一产品或新旧版本：

1. **法律主体**：运营方、著作权人、备案主体和协议签署方；
2. **品牌与产品**：品牌名、产品名、功能模块名及其官方表述；
3. **技术与入口**：域名、子域名、应用入口、重定向链、页面标题和服务协议；
4. **时间关系**：不同日期的官网公告、存档页面、版本说明和媒体材料。

域名重定向、旧链接统一导向新入口、页面视觉高度相似，只能证明当前入口关系或形成迁移线索，不能单独证明产品已更名、完全替代、技术同源或法律主体相同。只有证据闭环时才写“更名”“升级为”“由……替代”。

若多项公开迹象已稳定指向某种实际状态或不成文惯例，但企业没有作出正式声明，例如旧产品的入口、功能和用户路径已由新产品承接，应按以下流程处理：

1. 助手自行发现时，先在对话中向用户展示关键证据、替代解释、拟采用措辞和拟写入位置，等待用户同意后再写入报告；
2. 用户先发现并告知该现象时，可在独立复核后直接采用有限表述，无须重复征求同一事项的同意；但不得把用户观察本身升级为已核实事实；
3. 正文使用“当前公开入口及功能承接关系显示……”“实际呈现出整合或升级关系”等措辞，同时注明尚未发现正式更名或合并公告；不得写成企业已经官方确认；
4. 仅在该状态会影响分析对象边界、产品沿革、功能归属或竞品判断时简短说明；不改变结论的一般访问现象不单独扩写。

### 5.7 产品体系与技术术语分层
遇到企业自定义产品名或平台术语时，先查官方产品导航、独立产品页、帮助文档和发布公告，再判断其层级。不得因名称普通或含义宽泛，就把官方产品模块写成一般概念；也不得因官网出现专有名称，就断言它是独立收费 SKU、独立部署产品或成熟商业线。

至少区分：底层平台或操作系统、模型或 Agent、用户可见产品/应用模块、功能组件、开发接口、连接协议及一般行业概念。MCP 等协议或连接标准，不与 Agent、工作台或产品模块并列为同类产品。官方将某名称列入 Product 并设独立产品页时，可写“正式命名的产品模块”；是否独立定价、授权或部署，须另有公开证据。

API、插件、连接器、智能体 Skills 与 MCP 必须分别核验。只有官方明确使用 MCP 名称，或存在可核验的 MCP 文档、服务器、端点、配置或调用说明时，才能写“提供 MCP 服务/接入”。仅出现 API、工具调用、插件、OpenClaw/Workbuddy 等 Skills 接入或“兼容智能体”表述，不足以证明存在 MCP。检索后仍无法确认时写“未发现可核验的独立 MCP 服务”，不写成确定不存在。

正文首次出现可能影响理解的缩写、融资或产品术语时，用一句自然语言解释，不把报告扩写成教材。涉及 ARR、融资轮次、优先股、IPO、投前/投后估值、股权稀释、领投/跟投及退出机制时，按 [商业与产品术语口径](references/business_product_terms.md) 核对定义、口径和表达。

## 6. 事实、声明、推断三分法

任何关键陈述归入以下类型之一：

### A. 已核实事实
示例：官方价格页显示包年套餐为 1,280 元，包含 13,800 积分。

### B. 企业公开声明
示例：官网称其采用多路召回与交叉验证。

### C. 分析判断或推断
示例：该工作流设计有助于提高案件连续性，但尚不足以证明形成长期壁垒。

不得混淆三者。

三分法用于写作前和审稿时的内部判断，不要求在正文逐条贴标签，也不要求设置“公开表述—证据性质—本报告处理”表格。正文应直接采用与证据强度匹配的自然表述。

## 7. 逻辑审查框架

逐项检查：
- 因果关系是否成立；
- 比较对象是否同类；
- 时间范围和统计口径是否一致；
- 数据与结论是否匹配；
- 前提条件是否完整；
- 是否存在以偏概全或因果倒置；
- 是否把“有产品”写成“有成熟能力”；
- 是否把“企业声明”写成“已验证事实”；
- 是否把“早期付费信号”写成“规模化增长”；
- 是否把“工作流差异化”写成“不可复制壁垒”。
- 是否把“接触/入围/试点/签约/部署/上线/规模使用/续约”混写为同一商业验证阶段；
- 是否把注册用户、使用用户、付费用户、机构客户、坐席数混为同一口径；
- 是否把获奖、入选案例集或媒体报道等同于产品准确率、安全认证或客户续费证明。

### 7.1 企业发展驱动因素判断
介绍企业发展和管理团队前，先判断其核心发展驱动：

1. **创始人或主创团队特殊驱动**：只有当创始人或主创团队形成持续、可观察且足以让企业明显区别于同类公司的特殊影响时，才重点分析。典型影响包括强个人品牌或代言、对战略与产品风格的长期主导、对用户信任或渠道的不可替代贡献、独特组织文化或治理结构。人物履历丰富、公开表达与产品方向一致、参与融资或日常宣传，本身不足以认定为“强创始人驱动”；
2. **集团或关联企业特殊驱动**：只有当母公司、兄弟公司、控股股东、投资方、数据供应方或渠道伙伴实质改变企业的品牌、技术、数据、客户、资金、渠道或治理时，才单独分析其影响。普通投资、一般合作或未显示特殊作用的关联关系不单独扩写；
3. **产品和组织驱动**：若个人或关联企业影响有限，则不过度扩写人物故事，重点分析产品、交付和组织能力；
4. 不在正文机械加入“未发现创始人特殊影响”“未发现母公司特殊影响”之类的否定性段落。只有主体关系本身属于关键风险或用户明确要求时，才说明检索边界。

### 7.2 洞察总结写法
优先模仿参考附件中最成熟的洞察总结写法。每条洞察尽量形成“企业特有机制或矛盾—事实依据—约束条件—业务含义”的闭环，不把正文目录换一种说法重复一遍，也不使用与企业关联度低的模板化 SWOT。

洞察总结完成后检查：
- 是否能够明显区分该企业与同类公司；
- 是否由前文事实支持；
- 是否同时说明机会与成立条件；
- 是否避免把产品变化、签约、融资或曝光直接写成壁垒和规模验证。

### 7.3 同企业 AI 产品生态
分析某一法律 AI 产品时，不把研究范围机械限制在该产品单一前台。对同一企业运营或与核心产品存在明确账号、数据、模型、功能、渠道或商业协同的其他 AI 产品一并分析，包括 API 开放平台、MCP 或工具接口、模型平台、开发者平台、法律数据库、知识库、机构端工作台和垂直智能体。

至少说明：各产品的目标用户与功能定位、与核心法律 AI 的连接方式、共用能力、商业作用及是否形成产品生态。API 开放平台等基础设施型产品与前台助手同等重要，不得只在附录或一句话中带过。与法律 AI 缺乏明确联系的普通软件、非 AI 业务或仅因同属集团而存在的产品，不为凑全产品矩阵而扩写。

### 7.4 安全、隐私与专业责任边界
该部分重点分析数据输入与留存、模型或第三方服务调用、权限与隔离、用户删除或退出机制、生成内容复核要求、律师职业责任及产品免责边界。保持与报告目的相称的篇幅，不把它写成认证资质目录。

各类 ISO、等保、质量管理、信息技术服务或类似证书默认只作为背景核验材料，不在正文逐项罗列、解释或配图。只有证书与目标产品直接相关，并且会显著影响客户准入、安全判断、竞品比较或核心结论，或用户明确要求时，才在正文简要提及；其存在仅能证明特定认证范围及有效期内的符合性，不能自动证明法律 AI 的准确性、隐私实践或实际部署安全。

## 8. 结论强度控制

建议采用四段式结论：
1. 企业或产品是什么；
2. 当前已经证明什么；
3. 当前尚未证明什么；
4. 在什么条件下可以升级判断。

推荐平衡表述：

> 该企业是某细分领域中定位较鲜明的早期参与者之一。其在产品组织方式、场景模块化和使用门槛方面具有一定辨识度，但尚未形成可由公开信息验证的规模、数据、品牌或企业交付壁垒。若未来能够证明专业准确性、持续续费和标准化交付，其行业地位有望进一步提升。

避免使用“国内领先”“行业第一”“已形成壁垒”“必将成为代表性厂商”“高增长已验证”，除非证据充分。

## 9. 实名竞品对标方法

### 9.1 分组对标
不要把业务模式差异过大的企业放在同一张表直接排名。建议分为：国内直接或近似对标、国际能力标杆、数据库型平台、综合法律 AI 工作台、垂直诉讼工作流产品。

### 9.2 统一评分模型
推荐 100 分：

| 指标 | 权重 |
|---|---:|
| 产品场景适配 | 20 |
| 专业准确与可验证性 | 20 |
| 法律数据与知识底座 | 15 |
| 用户与商业验证 | 15 |
| 企业级交付与安全 | 15 |
| 产品生态与扩展能力 | 10 |
| 价格与使用门槛 | 5 |

每项 0—5 分：
- 5：充分公开证据或成熟商业验证；
- 4：较强，有较充分证据；
- 3：基本具备，但验证不完整；
- 2：仅有初步能力或企业声明；
- 1：明显较弱；
- 0：无能力或无证据。

指标得分 = 评级 ÷ 5 × 权重。

### 9.3 证据置信度
- A：官方数据 + 第三方/客户交叉验证；
- B：官方资料充分，缺少独立验证；
- C：媒体或有限公开信息；
- D：分析推断；
- N/A：无法评分。

不得为了凑齐表格而给无证据企业打分。

## 10. 市场规模与财务量化模型

仅在用户确认后新增。

### 10.1 TAM—SAM—SOM
TAM = 目标用户总数 × 理论年度客单价 + 目标机构总数 × 理论年度机构客单价。

SAM = 执业律师人数 × 诉讼业务占比 × 民商事占比 × 数字工具可接受比例。

SOM = 年新增有效线索 × 激活率 × 付费转化率 × 留存率 × 销售/交付产能。

### 10.2 收入拆分
个人订阅 = 月付用户数 × 月费 × 12 + 年付用户数 × 年费 + 体验套餐收入 + 积分增购收入。

团队版 = 团队客户数 × 平均账号数 × 单账号年费 + 协作/知识库/存储增购。

私有化 = 新增项目数 × 首次部署合同额 + 存量项目数 × 年度维护费 + 定制/扩容收入。

### 10.3 成本
变动成本：模型 API 或本地推理、OCR/ASR、云存储和流量、法律数据库授权、客服和支付费用。

固定成本：研发、法律知识工程、销售、客户成功、安全合规、办公行政、私有化交付团队。

### 10.4 盈亏平衡
盈亏平衡收入 = 年度固定成本 ÷ 综合边际贡献率。

### 10.5 估值
优先使用：收入倍数法、风险调整后的里程碑估值、融资反推法。

必须标注：本模型为情景测算，不代表企业预测或投资建议。

## 11. 图表与流程图处理

### 11.1 必查项目
标题、数据来源、数值、单位、坐标轴、图例、计算逻辑、正文结论一致性和视觉可读性。对成图和插入文档后的页面分别渲染检查，不以代码运行成功代替视觉验收。

### 11.2 修改规则
- 标签、单位、图例、排版：可直接修正；
- 改变数据含义或核心结论：先确认；
- 无法复现原图：保留醒目占位符。

同一融资轮次同时展示“单轮融资额”和“投后估值”等不同量级指标时，默认避免把两组数字标签放在同一锚点。优先采用分面图、双轴图、错位标注或“图形 + 数据表”；必须明确两者的单位、口径和轴归属。标签出现覆盖、交叉、贴边或与图例冲突时，调整偏移、对齐、字号、边距或图型后重新渲染，不能只删除其中一组数字。具体检查与修复见 [图表与字体视觉验收](references/chart_typography_qa.md)。

占位符示例：
- 【请手动插入原图：图 3—XX】
- 【请手动插入原流程图：XX 流程】
- 【请手动补充图片：原文第 X 页“XX”】

### 11.3 代码交付
如修改图表或流程图，必须提供可在 VS Code 直接运行的完整代码，包括依赖说明、数据、运行命令、输出文件、示例数据标注和原始数据缺失说明。

优先由系统自行生成并插入有真实依据的图表。确需用户生成时，优先提供可在 VS Code 运行的 Python 代码；除非用户指定其他环境，不只给伪代码、片段或只能在特定云笔记本运行的代码。

### 11.4 计划视觉材料未落地时的强制说明
如计划、提纲或优化方案拟加入组织图、流程图、网页截图、产品界面、数据图、照片或其他图片，但最终报告中无法生成、截取或插入，不得静默省略，也不得只保留无说明的占位符。

第一版交付时即在对话中直接提供获取说明，不等用户下载并打开报告后再补充；不写入报告正文、附录或单独交付文件，除非用户明确要求写入文档。必须为每一项未落地视觉材料提供：
1. **视觉材料名称**：与报告中的图号或占位符一致；
2. **获得方式**：提供可点击的原始直达链接、备用入口、页面名称、站内导航路径、搜索词或查询字段、截图范围和逐步操作；如需自行制图，提供可运行代码、原始数据及制图步骤；
3. **插入位置**：指出应放在报告的章节、小节、段落之后或具体占位符处；
4. **用途**：说明该图片用于证明、解释、比较或承接什么结论，不得仅写“增强美观”；
5. **证据与合规边界**：注明来源、访问日期、版权或授权风险、是否可能包含隐私或敏感信息，以及网页截图能证明和不能证明什么；
6. **替代方案**：如无法取得原图，说明可否改用自制示意图、表格、文字框或删除该视觉材料，并说明对结论和可读性的影响。

如提供代码，沿用 11.3 的完整代码交付要求；如提供网页入口，优先给出原始页面而非搜索结果页，并说明共享主链接与次级页面关系。不得只写“请获取价格页、产品截图、资质页面”等材料名称而不给链接和路径；直达链接可能失效时，同时给出官网首页、栏目路径和检索词。

网页截图还必须注明：页面链接、进入路径、建议浏览器缩放比例、要截取的标题/数据/界面范围、截图日期、需遮盖的账号或个人信息，以及截图应插入的正文位置。网页截图只能证明页面当时展示的内容，不能自动证明技术能力、实际部署或商业效果。

如用户回传图片，先检查裁切范围、清晰度、来源信息、隐私和敏感内容，再插入指定位置并补充图号、图题、来源和必要的证据边界。正式版中删除已完成的占位符、临时视觉清单和仅用于制作过程的版本说明。

## 12. 手动核验清单生成

手动核验清单只包含用户可通过公开网页、公开数据库或其本人合法登录后访问的页面取得的材料。只能通过向目标企业、员工、客户、合作方或投资方申请、访谈、询证或索取得到的非公开材料，一律不写入报告、待补材料、人工核验清单或后续行动建议，也不得作为分析成立的前提。

若公开证据不足，删除依赖该材料才能成立的内容，或改写为公开信息能够支持的有限结论；不得把不可完成的企业尽调任务转嫁给用户。不要为不影响当前结论的普通缺口生成泛化核验清单。

每条必须包含：
1. **材料名称与用途**：缺少什么，为什么会影响哪个判断；
2. **获取方式**：区分公开查询和用户本人合法登录后查询；提供可点击的原始直达链接、备用入口、页面名称、查询字段、站内路径和具体操作步骤；
3. **用户应回传的内容**：原始文件、完整页面、关键截图或字段，避免只回传口头结论；
4. **更新位置**：明确到章节、小节、表格或待替换段落，并说明补齐后新增或替换什么；
5. **更新节奏**：先完成不受影响的章节；相关材料由用户回传后，再定点更新受影响部分，不用重写整份报告。

生成清单时使用 [手动核验清单模板](references/manual_verification_checklist_template.md)。事实核验与图片获取必须分开表达；未落地视觉材料默认直接在对话中说明。

可定点补充的材料限于有公开或用户可登录入口的隐私政策、用户协议、与核心结论直接相关的公开备案或认证记录、公开安全白皮书、当前价格页、官方产品文档和公开采购或中标文件。不得仅为完善“安全资质”叙述而要求用户搜集各类证书。合同、验收材料、渗透测试摘要、内部模型与数据供应链清单、后台经营数据等仅由企业掌握时，不得列入。不得仅写“未检索到”，必须给出用户可执行的直达链接和查询路径。

没有剩余可执行补充事项时，删除“待补材料”章节；正式报告不保留空清单或无法完成的索取要求。

## 14. 正式交付要求

最终交付至少包括：
1. 优化后的完整报告；
2. 在对话中简要说明已实施优化、未实施的重大建议和版本关系；
3. 第一版交付时，仅在对话中列出会影响结论且可由用户公开获取或登录后获取的缺失材料，并提供直达链接、备用入口、页面路径、查询字段、操作步骤和定点更新位置；
4. 用户指定格式；
5. 如有图表修改，在对话或独立代码文件中提供完整代码；
6. 如有未落地视觉材料，在对话中逐项说明获得方式、插入位置、用途、证据或合规边界及替代方案。

正式报告中不保留已完成的制作说明、待补材料、视觉材料获取清单或版本关系章节。来源附录的每条通常只保留来源名称、来源类型、链接及必要日期，不逐条添加“用于”“作用”或用途说明。

推荐版本管理：V1.0 原稿 → V1.1 全面优化版 → V1.2 结论或专项方案版 → V1.3 竞品/量化模型扩展版。

必须明确每个版本基于哪个上一版本修改。

### 14.1 文档版式与字体
- 中文与西文字体分别显式设置，标题、分节标题、正文、表格和图题均不得依赖 Word 默认字体继承；
- 字体选择同时考虑可读性、粗细和环境兼容性。中文正文优先使用思源黑体/Noto Sans CJK SC Regular 或微软雅黑，标题使用 Medium/Semibold/Bold；西文优先使用 Arial 或 Aptos，并设置 East Asia、ASCII 和 High ANSI 字体字段；
- 不使用 Light、ExtraLight、Thin 等细字重作为正文或表格默认字体。若字体文件没有可靠字重元数据，改用可明确控制粗细的兼容字体；不得仅靠缩小字号或伪加粗补救；
- 如参考附件已有稳定、专业的字体体系，优先保持其视觉风格，同时保证目标环境可用；
- 交付前必须渲染逐页检查字体替换、实际字重、缺字、图题分离、表格截断、异常留白和分页问题；图表中的标题、坐标、图例和数据标签也要单独检查字重与清晰度。
- 所有数据表必须有语义明确的首行表头，并在 Word XML 中设置首行重复属性（`w:tblHeader`）；跨页表不得在续页丢失表头。使用 python-docx 时可给首行 `trPr` 添加 `OxmlElement("w:tblHeader")`。

## 15. 回复风格

不机械执行；不夸大；不替用户做无依据判断；先核验，再结论；先区分事实、声明和推断；重大修改先确认；结论尽量条件化；保持报告专业、清晰、正式。
