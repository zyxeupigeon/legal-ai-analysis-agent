# P3.1 成熟组件复用隔离评估

## 目标与边界

本阶段只验证成熟开源组件能否承担可独立替换的小功能，不改写 P2.3.4
FastAPI/Next.js 冻结路径，不替换法律 AI 产品身份闸门、主张—证据登记、矛盾日志、
结论强度控制或 Word 逐页视觉验收。

候选组件必须在隔离环境通过真实样本测试后，才可以进入正式适配层。组件流行度、
Star 数或项目自述不能代替本项目验收。

本原则包含两层复用：既寻找能够实现目标功能的成熟项目，也优先寻找能够发现、聚合、
评价这些项目的成熟开源工具。第二层“元发现工具”不能绕过第一层的证据要求，也不能
因为自身负责评分就免于许可证、维护状态、真实采用度和本地可运行性审查。

## 开源项目元发现管线

元发现采用可替换的多源管线，而不是依赖单一搜索器、单一评分或特定 Agent/MCP：

1. 先把目标拆成可独立验收的小功能，并给出输入、输出和不可退让的项目边界；
2. 通过 GitHub 原生搜索、Topic、成熟 Awesome 清单及其索引生成候选集；
3. 通过 GitHub 仓库元数据和可选的生态元数据服务补充发布时间、维护活动、发布、
   贡献者、下游依赖和许可证信息；
4. 使用 OpenSSF Scorecard 等成熟工具补充安全与维护风险信号，但不得把聚合分数当作
   自动采纳结论；
5. 阅读文档、许可证、变更记录和关键代码，并在隔离目录运行最小真实样本；
6. 只有功能完全匹配且验收通过的项目才可进入替换建议。仅近似匹配的项目只列出差异、
   风险和链接，交由用户决定，不自动替换；
7. 任一发现源不可用、收费、要求额外登录或返回冲突数据时，记录失败并继续其他来源，
   不得为了凑够候选而降低证据门槛。

所有元发现能力均为可选增强。任意合格 Agent 仍可仅凭公开网页与 GitHub 访问完成基本
候选发现；项目不得强制要求指定模型、模型 API、浏览器、MCP 或元发现服务。

## 2026-08-11 元发现工具初筛

### ecosyste-ms/awesome 与 ecosyste-ms/repos

- ecosyste-ms/awesome 是专门索引 Awesome 清单中开源项目的开源 API，适合作为人工
  策展候选的聚合入口；ecosyste-ms/repos 可补充仓库和生态元数据。
- 两个项目持续维护并公开 OpenAPI；服务端代码采用 AGPL-3.0，API 数据分别受其公开
  数据许可约束。因此优先调用公开 API，不复制服务端代码到本项目。
- 2026-08-11 实际无凭据请求 awesome.ecosyste.ms/api/v1/projects 返回 HTTP 402，
  与仓库文档宣称的公共限额不一致。当前不能把它设为稳定前置条件。

结论：OPTIONAL_SOURCE_BLOCKED。保留为候选生成与元数据增强源；只有接口恢复且真实
查询通过后才进入自动化适配器。

### OpenSSF Scorecard

- 项目成熟、持续维护，提供 CLI、REST API 和公开数据；本轮 REST API 实际请求成功。
- 能提供维护状态、许可证、危险工作流、依赖固定、漏洞和代码审查等风险信号。
- 官方明确说明各项检查属于启发式判断，存在误报、漏报，聚合分数不能代替对具体行为
  和功能匹配度的审查。

结论：CONDITIONAL_PASS。适合作为候选风险过滤器，不承担候选发现，也不能独立决定
是否替换。

### Awesome 清单、Track Awesome List 与 GrimoireLab

- sindresorhus/awesome 及各领域 Awesome 清单适合提供人工策展的高精度起点；
  trackawesomelist/trackawesomelist 可用于发现清单更新，但两者仍需回到原仓库核验。
- chaoss/grimoirelab 能做完整的软件开发分析，能力成熟但部署和数据采集链路较重，
  不符合当前“解压后由任意 Agent 使用”的轻量路径。

结论：Awesome 清单作为 PASS_DISCOVERY_SOURCE；Track Awesome List 作为可选更新源；
GrimoireLab 作为研究参考，不进入本地依赖。

## 2026-08-11 首轮结果

### MarkItDown 0.1.7

- 使用用户已提供的 P2.3.4 Word 测试稿进行只读转换。
- 核心 DOCX 转换成功，得到 2,106 个字符，能够保留中文标题、正文及 Markdown
  表格标记。
- 转换结果用于内容理解是可行的，但不保留 Word 的分页、字体、图表位置和完整视觉
  结构，因此不能替代 PDF/PNG 渲染与逐页检查。
- 标准安装会强制引入 Magika；当前网络环境多次在该依赖下载阶段超时。正式方案必须
  将 MarkItDown 定位为可选组件，并保留无需它也能读取 DOCX 的回退路径。

结论：`CONDITIONAL_PASS`。适合附件内容抽取，不适合作为默认硬依赖或视觉解析器。

### Crawl4AI 0.9.2

- 主包能够取得，但完整运行环境还需要 Playwright/Patchright、NumPy、LiteLLM、NLP、
  几何处理等较大的依赖集合。
- 在当前网络环境中，完整依赖安装未能在单次两分钟窗口内完成；未取得真实政府网页
  抓取结果，不能把 GitHub 项目说明当作本地通过证据。
- 依赖规模与“用户解压项目后使用任意现有 Agent”的轻量目标存在张力。

结论：`BLOCKED_NOT_REJECTED`。只能作为检测到可用时启用的增强抓取器，不能成为
项目启动或完整报告流程的硬性前置条件。完成安装和政府网页正文命中测试前，不进入
正式代码。

## 保留的项目自有能力

以下能力没有成熟组件能够无损替换：

- 产品身份歧义闸门；
- 企业、品牌、产品、API、MCP、连接器和 Skill 分层；
- 来源等级、主张—证据绑定及冲突日志；
- 事实、企业声明和分析推断三分；
- 证据不足时的结论降级或安全停止；
- 参考报告结构复刻、可编辑 Word 生成和逐页视觉修复；
- `validate_portable_agent_output.py` 的项目专项确定性验收。

## 隔离验收入口

使用 `scripts/evaluate_optional_components.py` 检查组件是否安装，并在提供样本时执行
真实转换。所有输出被强制写入 `agent_outputs/`，脚本不会安装依赖、读取 `.env` 或
调用冻结网页应用。

只有结果为 `passed`，且原有冻结基线和 P3.0 专项验收继续通过，组件才可以进入下一
阶段的适配器设计。
